# 1. 기능 동작 검증

 선택한 업무 과업 1개가 문서에 명확히 정의되어 있는가? (타겟 사용자와 입력과 출력 규격 포함)

 입력 템플릿이 1개 이상 제시되어 있으며, 그대로 복사해 재사용 가능한가?

 3종 이상의 모델 비교 결과가 표 또는 그에 준하는 구조로 정리되어 있는가? (비교 기준 4개 이상과 점수와 근거 포함)

 Few-shot 예시가 최소 3개 존재하며, 그중 1개는 모호한 입력에서 되묻는 흐름을 포함하는가?

 환각 검증 질문 5개 이상과 Pass 또는 Fail 판정 결과가 제출물에 포함되어 있는가?

 10턴 이상 대화 로그가 있으며, 중간 조건 변경이 반영된 결과가 확인 가능한가?

 미해결 기록에 어려움을 겪었던 과업이 2건 이상 있고 건마다 시도한 프롬프트와 막힌 이유가 함께 있는가?

# 2. 동작 구조 설계

 시스템 프롬프트, 유저 프롬프트, 입력 템플릿을 문서에서 어떻게 구분했고 각각을 나눈 이유가 무엇인지 설명할 수 있는가?

 프롬프트를 v1에서 v2로 개선하면서 무엇을 왜 고쳤는지 설명할 수 있는가?

 모델 비교에서 비교 기준과 모델별 점수를 무엇을 근거로 매겼는지 설명할 수 있는가?

# 3. 핵심 기술 원리 적용

 환각을 사실 오류로 정의하고 창의적 생성과 구분한 이유를 설명할 수 있는가?

 환각 검증에서 Pass 기준(A 와 B)과 Fail 기준을 어떻게 판정했는지 설명할 수 있는가?

 모델 선정 이유를 업무 과업 특성과 연결해 설명할 수 있는가?

 Zero-shot, Few-shot, 단계적 추론 유도 가운데 어느 기법을 적용했고, 해당 과업에 그 기법을 선택한 이유를 설명할 수 있는가?

 페르소나의 역할과 말투와 금지 사항을 그렇게 정한 이유를 업무 문제와 연결해 설명할 수 있는가?

# 4. 심층 인터뷰

 비용 제약으로 무료 모델만 사용해야 한다면 품질을 유지하기 위해 프롬프트와 프로세스를 어떻게 바꿀지 설명할 수 있는가?

 업무 정책(규정이나 수치)이 자주 바뀐다면 환각을 줄이기 위한 운영 전략을 설명할 수 있는가?

 10턴 이상에서 문맥이 끊기는 문제가 생겼다면 이를 해결하기 위해 프롬프트 구조를 어떻게 개선할지 설명할 수 있는가?

 작업 기록에서 작업을 어떤 단위로 나눴는지와 그렇게 나눈 기준을 설명할 수 있는가?
